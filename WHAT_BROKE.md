# What broke (running log)

Log every issue as it happens. It's the honest record of what went wrong and how it was fixed.

| # | Symptom (what I saw) | Root cause | Fix | Time lost |
|---|---|---|---|---|
| 1 | `require_key` said `OPENAI_API_KEY not set` even though `.env` was correct (I re-pasted the key twice) | `lib.sh` found the repo via `$BASH_SOURCE`, which is empty when sourced from **zsh** (macOS default shell), so it looked for `.env` in the parent folder | Fall back to `$0` (zsh sets it to the sourced file). Lesson: check the tooling before blaming the input | ~10 min |
| 2 | `setup.sh` printed "Done" but returned exit code 1 on re-run, so `setup.sh && verify.sh` chains would stop | EXIT trap in `lib.sh` (kills port-forwards) ended with `[ -n "$p" ] && kill`. With no port-forwards started, that test returns 1, and under `set -e` the trap's status became the script's exit code | `pf_cleanup` ends with `return 0`. Proved with old vs new lib under `set -euo pipefail` (exit 1 vs 0) | ~10 min |
| 3 | (Caught before it mattered.) The OpenAI Secret had a `kubectl.kubernetes.io/last-applied-configuration` annotation | Plain `kubectl apply` stores a full copy of the object in that annotation, so the key sat in a second place and would show in `kubectl describe secret` | Create the Secret with `kubectl apply --server-side` (no annotation). Deleted and recreated, then confirmed the annotation is absent and the key appears in 0 proxy log lines | ~5 min |
| 4 | First M3 log checks passed but printed garbled evidence (`[{"phase": "guard": "guard":`), and the loose grep (`guard.*mask`) could have matched the wrong thing | The access log's `agw.ai.guardrails` field is JSON with spaces inside; I split it on spaces | Read the raw log, then matched the exact JSON (`"action": "mask"` / `"action": "reject"`) and extracted fields with a regex. Also made 3c prove nothing reached OpenAI (403 line has **no token usage**), since `endpoint=api.openai.com` is logged even for rejects | ~5 min |
| 5 | (Found by the independent QA review.) A fake `sk-` key sent to **`/v1/embeddings`** got HTTP 200: the prompt guard was bypassed, and any caller could spend the key on embeddings | The `openai/*` model route serves several OpenAI endpoints. promptGuard covers chat/responses/messages but not embeddings | Gateway-level **endpoint allowlist** policy (only `/v1/chat/completions`, `/v1/models`, `/mcp`), fail-closed. New checks 3g prove embeddings and responses get 403 (`reason=Authorization`) and models still work. Also from the review: the JSON 403 body (3f), `ASIA` keys, stricter 3b/3d | ~20 min |
| 6 | MCP server pod stuck in `CreateContainerConfigError`; setup.sh timed out, so the backend/route never got applied | `runAsNonRoot: true` in the pod + `USER node` (a *name*) in the Dockerfile: kubelet can't prove a named user isn't root, so it refuses to start (fails safe) | `USER 1000` (numeric UID of `node`) in the Dockerfile, rebuild, `kind load`, restart | ~5 min |
| 7 | **Mutation test** (delete the M5 policy, re-run verify 5): check 5f "fake secret never exposed" still **PASSED** though `get-env` had just returned the secret. Also 5e passed with no policy at all | 5f: `echo "$big" \| grep -q` under `set -o pipefail`. `grep -q` exits on the first match, `echo` gets SIGPIPE, the pipeline returns non-zero, so "found" read as "not found" (only with large input, like 10 min of logs). 5e only checked that a get-env line existed, not that it was denied | Replaced all 17 pipe-into-`grep -q` tests with here-strings (`grep -q X <<<"$var"`); 5e now requires `reason=Authorization` + "authorization denied". Re-ran the mutation test: without the policy 5b–5f FAIL, with it 6/6 PASS. **Lesson: a test that never fails proves nothing; break the feature on purpose** | ~15 min |
| 8 | Hermes agent turn failed: `agent_incomplete`. Hermes log: *"context window of 8,192 tokens, below the minimum 64,000"* | With `provider: custom`, Hermes can't discover the model's window. It probes local-server endpoints on the gateway (`/props`, `/api/tags`, `/version`, all 404) and falls back to 8K | `model.context_length: 1047576` (gpt-4.1-mini's real window). Found by testing in `docker run` first, as planned | ~10 min |
| 9 | Every fresh agent session logs one `400` from OpenAI before the `200` | Hermes sends `reasoning_effort`, which gpt-4.1-mini (non-reasoning) rejects ("Unrecognized request argument"). Then, in a 10-min timebox I set, traced it in the source: the `custom` provider profile defaults an unset effort to `medium` unless the model is marked non-reasoning. **Fix:** `model_overrides.custom."openai/gpt-4.1-mini-2025-04-14".supports_reasoning: false`. Fresh sessions now log only 200s | ~12 min |
| 10 | `kind load docker-image` for the Hermes image: `ctr: content digest … not found` | Multi-arch image + Docker Desktop's containerd image store: kind imports `--all-platforms`, but only arm64 layers exist locally | The kind node pulls the image itself (`crictl pull`, own arch only) in setup.sh before the rollout | ~5 min |
| 11 | M7 check 7d (other pod → MCP server) printed nothing; and its first version would have **falsely passed** | (1) `kubectl run -i --rm` attaches too late and loses a 5-second command's output. Test with a pure TCP connect (`nc -z`), so only a refused/timed-out connection counts as blocked. Before the policy: REACHED; after: BLOCKED | ~10 min |
| 12 | After scaling the gateway to 0 and back, `verify.sh 1` failed check 1c | A `kubectl port-forward` dies when its target pod is replaced, but a stale listener can remain; `port_forward` reused any listener on 8080 (also flagged by the M5 review) | `port_forward` reuses a listener only if it answers HTTP; otherwise it kills the stale kubectl and starts a fresh one. | 13 | Fail-closed test (gateway scaled to 0): the agent answered nothing for 90 s+ (looked like a hang) | Hermes' `agent.auto_recovery_cycles: 5` keeps waiting and retrying a "transient outage" for up to ~4 min (15/30/60/60/60 s) | `auto_recovery_cycles: 0`.
